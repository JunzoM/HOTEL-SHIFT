# FIXED558 全体性能の再最適化

## 1. 現在のコードのボトルネック（遅い原因）

### 人件費の週別警告

選択店舗の3年分の配列を作り、全行で日付解析・週の算出・月末計算を繰り返していた。対象月の前後を含めた週だけを先に用意し、既存の日付索引から対象行だけを取得する方式へ変更。週のラベルも週ごとに一度だけ生成し、集計キーはUUID文字列からUUIDとDateの構造体へ変更した。大きな履歴キャッシュは追加していない。

### 月・週シフト編集

編集件数にかかわらず店舗全履歴をグループ化していた。既存の日付索引から対象日の位置情報だけを取り出し、比較に使う行も必要時だけ参照する。開始・終了の入力検証や変更前スナップショットの確認は維持。

通常の更新（追加・削除なし、ID同一）では配列順が変わらないため、対応位置を直接更新する。追加・削除・ID差替えは従来の全件処理を維持。全体のID重複チェックは残し、UUIDの中間配列だけをlazy変換で除去した。希望休も全申請集合を構築せず、対象セルの既存索引へ照会する。同じ日付の検証は一度にまとめ、空編集は保存保護・店舗・版を確認した後にすぐ返す。

### 実測

10店舗×各50人×1096日＝548,000行。休みを含め毎日1行、日勤と夜勤を混在。Swift -O、ローカルMac、旧FIXED557と現行メソッドを同一ハーネスで比較。週別警告は旧3回・新5回、編集は各3回の中央値。索引は構築済み。

| 処理 | FIXED557 | FIXED558 |
| --- | ---: | ---: |
| 週別警告の集計（キャッシュ未使用） | 2938.89ms | 2.92ms |
| 1セル編集 | 241.30ms | 131.28ms |
| 50セル編集 | 243.54ms | 132.42ms |
| 空編集 | 91.19ms | 0.001ms未満（微小値は測定精度に依存） |

週別警告の走査対象は54,800行から1,750行、日付の準備は35日。UUIDの中間配列は要素容量で8,768,000 bytes＝約8.4MiBを除去。これはアプリ全体のRSSの実測減少量ではない。編集検証の店舗全履歴配列と行ごとのグループ配列も対象日の位置情報へ縮小した。

描画・JSON保存・Cloud同期・実機I/Oは測定外。アプリ全体やiPhone/iPadが同じ倍率で速くなるという意味ではない。

## 2. 計算量（Time/Space Complexity）

N＝全シフト、L＝店舗全履歴、P＝対象週のシフト、D＝対象日数、K＝編集対象日の候補行、B＝編集数、S＝スタッフ数、W＝週数、R＝警告数、Q＝店舗の全申請、T＝編集対象セルに属する申請。辞書照会は平均O(1)として扱う。

| 処理 | 変更前の時間 | 変更後の時間 | 変更前→変更後の追加作業メモリ |
| --- | --- | --- | --- |
| 週別警告 | O(L+R log R)（日付解析等をL回） | O(D+P log P+S+R log R) | O(L+SW) → O(P+D+SW) |
| 通常シフト更新 | O(N+L+Q+B) | O(N+K log K+D+B+T) | O(N+L+Q+B) → O(N+K+D+B) |
| 追加・削除・ID差替え | 全件配列の再構築が必要 | O(N+K log K+D+B+T) | 引き続きO(N)が中心 |
| 空編集 | O(L+Q+S) | O(1) | O(L+Q+S) → O(1) |

週別警告ではP件の元の順序を保つための位置ソートがP log Pとなる。時間の大きな定数要因だった文字列日付解析を全履歴分行う必要がなくなった。既存の上限付きキャッシュも維持し、同じ版・月のキャッシュ参照はO(1)。UIが警告を並べる描画コストは別。

シフト更新はコピーオンライトと全件IDチェックのためO(N)が残り、O(B)になったとは扱わない。削除したUUID配列のメモリもO(N)だったが、他のO(N)領域が残るため、編集処理全体の空間計算量は同じO(N)のまま。今回は定数分の削減と、全履歴グループ化・不要な日付解析の除去が中心。

全データ本体と既存索引の常駐O(N)、初回索引構築、全件JSON保存・バックアップのO(N)は維持。写真や文字列の長さも実際のメモリ使用量に影響する。
