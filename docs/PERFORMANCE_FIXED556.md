# FIXED556 性能最適化

## 1. 現在のコードのボトルネック（遅い原因）

- PDF生成のスナップショットと簡易プレビューが全店舗・全期間のシフトを参照し、毎回全件を走査していた。既存の日付索引で対象月／対象日だけを抽出する方式に変更。元の配列順と重複行の先勝ち動作を維持。
- 希望休の一括承認では、申請ごとに全シフトを走査し、申請・スタッフも毎回線形検索していた。対象日の位置だけを取得してセル別にグループ化し、申請IDとスタッフIDも処理中だけ索引化。追加した休みを作業用マップにも登録するため、同一スタッフ・同日の別申請でも休みが重複しない。
- ホームの年間グラフは店舗の全履歴を毎回集計していた。対象年の月索引から集計し、版・店舗・年をキーに12個の数値だけを既存の上限付きキャッシュに保持。
- 店舗画面の件数表示で履歴全行の配列を作っていた。索引の要素数を直接返して配列生成を除去。

### 実測

ローカルMac、Swift -O、実際のデータ型・旧版／新版のメソッド・索引更新処理で測定。10店舗×各50人×1096日＝548,000行（休みを含め毎日1行）。対象月31日＝1550行、一括承認200件。検索は7回、一括承認は3回の中央値。

| 測定対象 | FIXED555 | FIXED556 | 比率 |
| --- | ---: | ---: | ---: |
| 簡易プレビュー用データ検索 | 109.93ms | 5.72ms | 約19.2倍 |
| 200件の一括承認処理 | 5453.75ms | 136.50ms | 約40.0倍 |
| PDF生成へ渡すシフト数 | 548,000行 | 1,550行 | 約99.7%削減 |

検索と一括承認の結果一致、休み未登録・重複セルの扱いも確認。PDF描画・SwiftUI描画・JSON保存・クラウド同期・端末のI/O時間は測定に含まない。iPhone/iPadの実機速度を示す値ではない。

PDFスナップショットは従来全履歴の共有配列を保持しており、コピーオンライトのため取得時に全件コピーしていたわけではない。今回は対象月だけを渡すことで、バックグラウンド生成中に全履歴配列の古い版を保持することを避ける。配列要素の容量換算では192 bytes×548000＝約100.3MiBに対し、対象月1550行は約0.284MiB。文字列等の別領域を含まず、アプリ全体のRSSの実測削減量を示すものでもない。

## 2. 計算量（Time/Space Complexity）

N＝全シフト件数、L＝対象店舗の全履歴、M＝対象月／表示範囲の行数、D＝対象日数、B＝承認申請数、Q＝全申請数、S＝対象スタッフ数、K＝承認対象日の候補シフト数、Y＝対象年の行数。辞書・集合の検索は平均O(1)として評価。

| 処理 | 変更前の時間 | 変更後の時間 | メモリ |
| --- | --- | --- | --- |
| プレビュー用検索 | O(N+D) | O(D+M log M) | 両方O(M+D)。新しい全件キャッシュは作らない |
| PDF抽出・描画準備 | O(N+S log S+SD) | O(D+M log M+S log S+SD) | 非同期処理へ渡す保持対象をO(N)からO(M)へ限定。取得時のコピー有無とは別 |
| 一括承認 | O(B(N+Q+S)+N+L) | O(N+L+Q+S+B+K log K) | 作業用O(Q+S+K+B)。変更配列のCOWを含めると両方O(N+Q)の範囲 |
| 年間グラフ | O(L)／再描画 | 初回O(Y)、同じ版・店舗・年の再描画O(1) | 月単位の一時配列＋12数値。旧方式のO(L)一時配列を回避 |
| シフト件数 | O(L) | O(1) | O(L)の一時配列からO(1) |

対象月の索引取得では、旧配列順を保つため位置をソートするM log Mが残る。一括承認は配列変更時のCOWと既存の索引更新で全件に触れるため、処理全体をO(B)とは扱わない。

初回索引構築はO(N+Q+S)、既存索引の常駐メモリもO(N+Q+S)のまま。本測定の索引構築は約2180ms。全件JSON保存・バックアップもO(N)のままで、保存形式や同期方式は変更していない。
